# RAIHANA HIS UI/UX V2

This prompt is part of a phased frontend redesign for an Enterprise Hospital Information System (HIS) built on Frappe.

## Global non-negotiable rules

- Frontend only unless explicitly approved.
- Do not alter DocTypes, database structure, permissions, APIs, backend workflows, naming series, routing logic, or ERP business logic.
- Preserve Frappe authentication, sessions, role permissions, routes, forms, list views, reports, notifications, and existing data behavior.
- When a requested UX improvement requires backend work, document it under `Backend dependency — not implemented`.
- Do not replace working Frappe behavior with mock data.
- Build reusable components instead of page-specific visual hacks.
- Clinical safety, speed, clarity, accessibility, and data integrity override visual effects.
- No visual effect may hide, delay, obscure, reorder, or reduce the readability of clinical information.
- Support Arabic RTL and English LTR from the beginning.
- Meet WCAG 2.2 AA at minimum.
- Respect `prefers-reduced-motion`.
- Keep dense clinical surfaces fast and calm.
- Take screenshots and provide a changed-files report at the end of each phase.
- Stop after the requested phase and wait for explicit approval.

## Required research approach

Before implementation, inspect the existing codebase and identify:
- Frappe version and frontend architecture.
- Whether the current surface uses Frappe Desk, Frappe UI, Vue, React, Jinja, or custom pages.
- Existing assets, theme files, hooks, build pipeline, and component conventions.
- Existing routes and role-based navigation.
- Current UI defects and inconsistencies.

When internet access is available, research current open-source interaction and component patterns from:
- Motiq
- 21st.dev
- Aceternity UI
- Magic UI
- Origin UI
- React Bits
- Motion Primitives
- Animata
- Cult UI
- Uiverse
- shadcn/ui
- Radix UI
- HeroUI
- GitHub open-source projects

Also study product patterns from Linear, Raycast, Stripe, Vercel, Notion, GitHub, Slack, and modern healthcare systems.

Do not copy an entire product or paid component. Use only legally reusable open-source code with a compatible license, record the source and license, and adapt it into one original Raihana design language.

# PHASE 2 — MODERN DASHBOARD + INTERACTIVE STAT CARDS

## Context

Continue from the approved Phase 1. Reuse the exact established tokens, shell, motion language, accessibility rules, and components. Do not create a second design system.

## Objective

Create a dashboard that answers “What needs attention now?” within three seconds while still delivering a premium, modern experience.

## Scope

### 1. Dashboard composition
Include only data supported by the current Frappe system, such as:
- today's appointments,
- waiting patients,
- pending laboratory work,
- open radiology work,
- active admissions,
- occupancy,
- unpaid/unfinished billing items,
- urgent operational alerts,
- user-specific tasks.

Do not invent unsupported metrics.

### 2. Card hierarchy

Use three card classes:
- Critical attention cards: visually clear, not decorative.
- Operational stat cards: calm, compact, scannable.
- Navigation/feature cards: may use richer interaction.

Allowed rich effects on selected navigation/feature cards:
- Border Beam,
- pointer spotlight,
- soft glow,
- animated icon,
- subtle elevation,
- spring hover.

Disallowed:
- continuous distracting motion,
- glowing safety warnings,
- Border Beam on every card,
- hover movement that makes clicking difficult,
- animations that obscure values.

### 3. Bento layout

Use a responsive Bento-style composition only when it improves hierarchy. It must:
- preserve a predictable reading order,
- work in RTL/LTR,
- avoid awkward empty gaps,
- collapse cleanly on tablets/mobile,
- maintain consistent spacing and card anatomy.

### 4. Quick actions

Add a clear quick-action area using the approved permission model:
- register patient,
- create appointment,
- begin encounter,
- create lab/radiology request,
- open billing,
- other real supported actions.

Use explicit labels. Do not rely on icons alone.

### 5. Interaction

- cards reveal secondary actions on hover/focus without hiding core information,
- values may count/reveal once on load,
- staggered entry animation is allowed once,
- filters and time ranges update smoothly,
- notification/toast feedback is concise,
- focus behavior mirrors hover behavior.

### 6. States

Implement:
- skeleton loading,
- empty state,
- partial data state,
- permission-limited state,
- recoverable error,
- stale-data indicator where supported.

### 7. Drag/drop and customization

Do not add freeform drag-and-drop by default. First assess whether user customization is needed. If implemented:
- restrict it to non-clinical dashboard widgets,
- include reset-to-default,
- preserve keyboard accessibility,
- prevent hiding mandatory alerts.

## Required output

1. Data-source map for every widget.
2. Dashboard implementation.
3. Selected rich-interaction cards with rationale.
4. RTL/LTR, light/dark, desktop/tablet/mobile screenshots.
5. Loading/empty/error evidence.
6. Keyboard and reduced-motion evidence.
7. Changed-files report.
8. Stop and wait for approval.
