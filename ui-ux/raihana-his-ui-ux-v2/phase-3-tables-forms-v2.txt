# RAIHANA HIS UI/UX V2

This prompt is part of a phased frontend redesign for an Enterprise Hospital Information System (HIS) built on Frappe.

## Global non-negotiable rules

- Frontend only unless explicitly approved.
- Do not alter DocTypes, database structure, permissions, APIs, backend workflows, naming series, routing logic, or ERP business logic.
- Preserve Frappe authentication, sessions, role permissions, routes, forms, list views, reports, notifications, and existing data behavior.
- When a requested UX improvement requires backend work, document it under `Backend dependency — not implemented`.
- Do not replace working Frappe behavior with mock data.
- Build reusable components instead of page-specific visual hacks.
- Clinical safety, speed, clarity, accessibility, and data integrity override visual effects.
- No visual effect may hide, delay, obscure, reorder, or reduce the readability of clinical information.
- Support Arabic RTL and English LTR from the beginning.
- Meet WCAG 2.2 AA at minimum.
- Respect `prefers-reduced-motion`.
- Keep dense clinical surfaces fast and calm.
- Take screenshots and provide a changed-files report at the end of each phase.
- Stop after the requested phase and wait for explicit approval.

## Required research approach

Before implementation, inspect the existing codebase and identify:
- Frappe version and frontend architecture.
- Whether the current surface uses Frappe Desk, Frappe UI, Vue, React, Jinja, or custom pages.
- Existing assets, theme files, hooks, build pipeline, and component conventions.
- Existing routes and role-based navigation.
- Current UI defects and inconsistencies.

When internet access is available, research current open-source interaction and component patterns from:
- Motiq
- 21st.dev
- Aceternity UI
- Magic UI
- Origin UI
- React Bits
- Motion Primitives
- Animata
- Cult UI
- Uiverse
- shadcn/ui
- Radix UI
- HeroUI
- GitHub open-source projects

Also study product patterns from Linear, Raycast, Stripe, Vercel, Notion, GitHub, Slack, and modern healthcare systems.

Do not copy an entire product or paid component. Use only legally reusable open-source code with a compatible license, record the source and license, and adapt it into one original Raihana design language.

# PHASE 3 — HIGH-PERFORMANCE TABLES + SAFE FORMS

## Context

Continue from approved Phases 1–2. Reuse the same component library and tokens.

## Objective

Create the fastest, clearest, and safest high-traffic data surfaces in the system.

## Absolute visual rule

Do not use Border Beam, pointer spotlight, mouse-follow glow, magnetic motion, parallax, or decorative glass effects inside tables and forms.

Premium quality here comes from:
- alignment,
- density,
- typography,
- focus management,
- keyboard speed,
- immediate feedback,
- strong empty/loading states.

## Scope

### 1. Enterprise data table

Support where technically valid:
- sorting,
- filtering,
- global and column search,
- pagination,
- sticky header,
- row selection,
- bulk actions,
- column visibility,
- saved views if supported,
- responsive density,
- keyboard row navigation,
- clear status badges,
- contextual row actions,
- empty/loading/error states,
- virtualization recommendation for large datasets.

Use a subtle ≤150ms row hover/focus treatment with no bounce.

### 2. Patient list example

Implement a realistic patient list using current system fields only. Prioritize:
- patient name,
- MRN/ID,
- age/sex,
- contact,
- last/next encounter when supported,
- alerts/status when supported,
- clear action entry point.

No sensitive information should be exposed to unauthorized roles.

### 3. Form system

Create:
- text/number input,
- textarea,
- select/combobox,
- date/time controls,
- checkbox/radio/switch,
- segmented control where appropriate,
- file attachment where supported,
- helper text,
- required marker,
- error/warning/success states,
- field group/section,
- sticky action footer for long forms.

Floating labels are allowed only if they remain clear after autofill and with long Arabic labels.

### 4. Registration/intake example

Apply the form system to one real workflow without changing backend behavior.

### 5. Form interaction

- visible focus ring,
- input feedback ≤150ms,
- error uses icon + text + color,
- preserve entered values after recoverable errors,
- warn before leaving with unsaved changes where supported,
- clear save/submission states,
- no animated label or validation that reduces legibility.

### 6. Context menus and shortcuts

Optional contextual menus may be used for advanced row actions only when:
- all actions are also available through visible accessible controls,
- permissions are honored,
- keyboard access is supported.

## Required output

1. Table/form pattern rationale.
2. Reusable table and form components.
3. Real patient-list and registration examples.
4. Performance and virtualization assessment.
5. Keyboard, screen-reader, RTL, and reduced-motion evidence.
6. Changed-files report.
7. Stop and wait for approval.
